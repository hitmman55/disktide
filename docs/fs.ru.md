# Работа с файловыми системами и совместимость

Здесь описано, как DiskTide взаимодействует с файловой системой и какие возможности доступны на разных типах файловых систем.

## Поддержка платформ

Основной сканер использует кроссплатформенные функции Python: os.scandir, os.stat и os.path. Системные запросы изолированы в collectors/platform/. В Linux применяются procfs, sysfs и дополнительные команды; macOS, Windows и неизвестные платформы используют осторожные адаптеры. При отсутствии данных адаптер возвращает структурированную причину недоступности, а не исключение в сканер или интерфейс.

| Интерфейс | Назначение | Запасной вариант |
|---|---|---|
| /proc/meminfo | Доступная память | 0 MB; ограничение по низкой памяти не применяется |
| /proc/mounts | Определение типа файловой системы | unknown, осторожное предположение о локальном диске |
| /sys/block/*/queue/rotational | Различить HDD и SSD | None; решение по выборке метаданных или последовательное сканирование |
| os.sched_getaffinity(0) | Число CPU после cpuset | os.cpu_count() |
| /proc/self/cgroup и cpu.max / cpu.cfs_quota_us | Число CPU после квоты | Квоты нет; применяется только cpuset |
| memory.max / memory.limit_in_bytes | Память после ограничения контейнера | Только общая память из /proc/meminfo |
| os.getloadavg() | Нагрузка системы | (0, 0, 0), без снижения числа потоков |

Параметры cgroup нужны потому, что стандартные сведения о CPU и памяти не видят лимиты контейнера. sched_getaffinity сообщает cpuset, но docker run --cpus=1 задаёт квоту и оставляет видимыми все ядра. Поэтому на 64-ядерном хосте программа могла считать доступными 64 CPU. /proc/meminfo в контейнере также показывает память всего хоста: при --memory=512m на машине с 256 GB программа могла думать, что свободно около 200 GB, и не переходила на последовательный режим при памяти меньше 512 MB. Проверяются обе иерархии cgroup — от группы процесса до корня; действует самый строгий предел. Квота означает выделенные хосту ресурсы, поэтому общая нагрузка машины перестаёт ограничивать сканирование. disktide doctor показывает эти данные в блоке Platform.

В macOS нет /proc и /sys. Сканирование работает, а сведения о монтированиях, устройствах и носителях показываются как недоступные в disktide doctor и Обзоре ФС. Если автоопределение носителя недоступно, задайте workers явно.

Обзор ФС использует результаты тех же адаптеров. Если платформа не умеет перечислять монтирования или lsblk, интерфейс показывает состояние функции, причину и способ исправления вместо пустой панели.

В Windows работают os.scandir и os.stat, но нет os.getloadavg() и os.sched_getaffinity(). Главная проблема в том, что проект не испытывался на Windows, а возможности терминала, от которых зависит TUI, могут не работать в cmd.exe. Textual частично поддерживает Windows Terminal.

## Все обращения к файловой системе

### Сканирование — scanner/scheduler.py и scanner/accel.py

На каждый каталог сканер открывает дескриптор, получает его метаданные, перечисляет прямые элементы и закрывает дескриптор. Для недоступного каталога отдельно запрашиваются его собственные размер и идентичность. По умолчанию применяется небольшой модуль C; запасной вариант на Python выполняет ту же работу через os.scandir и DirEntry.stat(follow_symlinks=False). Каждый поток одновременно держит не более двух файловых дескрипторов.

Собираются метаданные каждого элемента, включая каталоги: логический размер st_size, выделенные блоки st_blocks × 512 (если платформа поддерживает их), устройство и inode, число жёстких ссылок, время изменения и тип. Для ссылок путь и тип цели заполняются по запросу. Не собираются права доступа, владелец uid/gid, расширенные атрибуты, ACL, время создания, коэффициент сжатия и физические блоки, занятые снимками.

Нативный считыватель выполняет обход каталога и fstatat для всех обычных элементов в одном освобождении GIL; запасной Python-считыватель возвращает те же данные. Тип элемента обычно берётся из d_type, а если файловая система его не сообщает — определяется через stat. Полный путь собирается в Python и хранится в FSNode.path, он не передаётся ядру. Совместимый рекурсивный walker остаётся в scanner/walker.py для диагностики и tool-скриптов; он рекурсивен по стеку Python и не предназначен для очень глубоких деревьев. Подробности о GIL приведены в [Архитектуре](architecture.ru.md#odno-osvobozhdenie-gil-na-katalog).

### Глубокие деревья

PATH_MAX (4096 байт в Linux) ограничивает аргумент пути для одного системного вызова, а не глубину дерева. Сканер не формирует полные пути к потомкам: корневой путь открывается небольшими отрезками, каждый следующий — относительно дескриптора предыдущего. Поэтому цепочка из 1200 каталогов с короткими именами сканируется до конца. Ранее обход останавливался на уровне 442, считая ошибку имени длиннее PATH_MAX ошибкой доступа.

Пути символических ссылок длиннее PATH_MAX тоже классифицируются через дескриптор родительского каталога. Однако очистка (корзина, карантин, удаление) пока формирует полный путь для shutil и спецификации корзины. Для пути длиннее 4096 байт действие завершается ошибкой до переименования или удаления. Удаление каталога, содержащего такой путь, работает через относительный к дескриптору обход; указать его потомка напрямую нельзя.

### Обработка символических ссылок

Ссылки **никогда не обходятся**. Ссылка хранится как лист дерева с собственным размером (stat без перехода по ссылке), а не размером цели. Это исключает бесконечную рекурсию, повторный подсчёт общей цели и прибавление содержимого ссылочного каталога к родителю.

Классификация цели отложена до первого использования. При создании узла измеряется только сама ссылка; readlink и stat цели выполняются, когда открыта панель Подробностей или клавиша i переходит в ссылочный каталог. Результат сохраняется в узле и повторное обращение ничего не стоит. Чтобы в типичном запуске disktide ~ сразу были видны цели ссылок верхнего уровня, движок заранее классифицирует не более 100 ссылок в корне. Ссылки глубже по дереву остаются ленивыми. Так добавляется не более примерно 60 мс задержки на медленной сети, но исключаются минуты ожидания для корневого каталога с сотнями тысяч ссылок. При любом варианте сканер не проходит по ссылке.

### Ошибки и полнота охвата

Каждый файловый элемент обрабатывается отдельно. Если невозможно прочитать сам каталог, ошибка записывается в узел и обход продолжается; ошибка отдельного элемента пропускает его. Частичный результат всё равно формируется. Ошибки хранятся в FSNode.error и показываются в подробностях TUI.

Недостаток данных никогда не превращает метрику в «Unavailable». Недоступный каталог учитывает собственные блоки, полученные из родительского каталога, но не содержимое. Каталог, достигший max_depth, учитывается аналогично. Исчезнувший элемент, исключённое псевдомонтирование, граница файловой системы или обнаруженный цикл предков не вносят содержимого. Пробелы отражаются счётчиками inaccessible, depth_limited, excluded и vanished, а в интерфейсе — строкой Coverage: partial.

None в allocated_size / unique_allocated_size означает только отсутствие st_blocks на платформе: тогда число отсутствует у всех узлов. Два случая недоступности — каталог, который нельзя открыть, и каталог, чьи элементы нельзя stat — оба учитываются как недоступное поддерево и показывают числовую нижнюю оценку, а не None.

**Изменение дерева во время обхода не означает отказ доступа.** ENOENT, ESTALE или ENOTDIR означают, что родитель перечислил элемент, но тот исчез до запроса метаданных. Такие узлы учитываются как vanished и не входят в inaccessible, ошибки прогресса, события AccessError или статус неполного результата. Исчезнувший до обработки каталог помечается vanished без error. Корень — исключение: несуществующий корень остаётся неверным аргументом. Остальные ошибки, включая PermissionError, учитываются как прежде.

### База мониторинга и снимков

Для новой установки SQLite хранится в ~/.local/share/disktide/data.db. Если там ещё нет новой базы, но есть ~/.local/share/sizetrail/data.db или ~/.local/share/fsmonitor-cli/data.db, DiskTide продолжает использовать наиболее новую старую базу, чтобы сохранить историю мониторов и очистки. Каталоги XDG создаются при необходимости. Перед обновлением схемы SQLite API резервного копирования создаёт data.db.pre-v11.bak.partial, затем атомарно переименовывает его в data.db.pre-v11.bak. Исходная база не удаляется и автоматически не перезаписывается.

Путь и ID мониторов хранятся как абсолютные строки. Пути элементов нормализуются, затем интернируются в paths.path и используются целочисленными идентификаторами в базовых и дельта-снимках. В базе также хранятся аренды и состояние мониторов, закрепления, происхождение агрегированных снимков, аудит хранения истории и события оповещений. Эти таблицы не запускают дополнительных обходов файловой системы.

SQLite работает с journal_mode=WAL (несколько читателей, один писатель) и foreign_keys=ON. Миграция схемы транзакционная. Если настройка записи или миграция не удалась, но файл читается, история доступна только для чтения; при повреждённом файле сканирование продолжается с ухудшенным репозиторием в памяти. На сетевом диске база работала бы медленнее; стандартный каталог XDG располагается локально.

### Необязательные события файловой системы

Основная установка не вызывает нативный механизм наблюдения. В Linux дополнение disktide[watch] предоставляет inotify-simple через отложенную проверку зависимости. Активный монитор рекурсивно добавляет наблюдение на каталоги с учётом one_file_system, исключения псевдофайловых систем и каталогов снимков, максимальной глубины и запрета перехода по ссылкам. Внутрь снимков наблюдение не входит; корень монитора, как и корень сканирования, является исключением. По возможности новые каталоги начинают отслеживаться до обработки следующих событий.

Механизм передаёт нормализованные подсказки о создании, изменении, удалении, перемещении, переполнении очереди, потере корня и ошибке backend. Пары переименования соединяются по cookie; неподтверждённое перемещение после ограниченного ожидания становится удалением. Переполнение, предел числа наблюдений, размонтирование, замена корня, перезапуск backend и истёкшая аренда переводят монитор в ухудшенное состояние и требуют полной сверки.

Обычные события объединяются DirtyPathTracker и направляются к соответствующему родительскому поддереву. Локальная сверка использует тот же ScanService, метрику и политику, но не записывает снимок. Только периодические, ручные и восстановительные полные обходы являются авторитетными. Поток событий не является журналом аудита файловой системы; простой процесса не восполняется историей событий.

### Оповещения о ёмкости

Правила свободного места и inode вызывают os.statvfs(rule.path) после сохранения снимка монитора. Получаются только метаданные ёмкости; путь правила не обходится. Правила размера, роста и нового крупного элемента используют уже сохранённые показатели снимка и не выполняют дополнительных обращений к файловой системе.

### Настройки

Конфигурация ищется с учётом XDG_CONFIG_HOME и ~/.config, при необходимости создаётся родительский каталог. Файл читается как TOML, при записи используется текстовый формат TOML.

### Очистка

Поиск кандидатов обычно работает по уже собранному дереву FSNode. Правила родительских индикаторов отдельно проверяют наличие файлов вроде package.json или Cargo.toml рядом с кандидатом. Встроенные правила загружаются из пакета, пользовательские TOML-наборы — из ~/.config/disktide/cleanup-rules/. Схема правил описательная и не поддерживает shell-команды, Python-код или исполнители.

До создания плана считывается идентичность цели без изменения файловой системы. Перед действием заново проверяются устройство, inode, тип, время изменения, размер и содержимое каталога; корень и точки монтирования защищены. Изменения выполняются относительно открытых дескрипторов каталогов с запретом перехода по ссылкам. Карантин должен принадлежать текущему пользователю, иметь режим 0700 и находиться на том же устройстве. Вместо атомарного переименования копирование с удалением не используется.

У карантина есть компактный ledger и блокировка для учёта вместимости; манифесты сканируются только при явном аудите, восстановлении или обработке прерванного состояния. Отмена повторно проверяет исходный путь и inode изолированного объекта; восстановление возможно, если путь свободен. Очистка карантина также проверяет манифест и идентичность и удаляет только изолированный объект после точного подтверждения PURGE <plan-id>. Системную корзину она не перечисляет и не очищает. История отдельно учитывает перемещённые, удалённые, фактически освобождённые и восстановленные байты.

Безвозвратное удаление не является действием по умолчанию и доступно только после подтверждения для конкретного плана. На поддерживаемых POSIX-системах файл или ссылка перемещаются в промежуточное имя рядом с собой, после чего удаляются через дескриптор каталога. Прямое удаление каталога заблокировано: сначала его содержимое должно попасть в карантин, откуда удаляется обходом без перехода по ссылкам. CLI и TUI могут обращаться к этому механизму только через CleanupService, после повторной проверки и записи аудита. Правила detection-only не могут вызывать операции перемещения или удаления.

### Экран приветствия

Дополнение пути использует os.scandir и os.path: раскрывает ~, выделяет родительский путь и часть имени, проверяет, что родитель — каталог, перечисляет его записи, добавляет / к каталогам и разрешает путь перед передачей сканеру.

### Системная информация и адаптеры

scanner/sysinfo.py сохраняет совместимый интерфейс настройки числа потоков. Он объединяет системные адаптеры с ограниченной выборкой метаданных каталогов и записывает запрошенное и итоговое число потоков с причиной. Linux-запросы находятся в collectors/platform/linux.py. Каждый результат имеет состояние доступности и причину.

Используются число CPU, affinity, средняя загрузка, /proc/meminfo, /proc/self/mounts, разрешение символических ссылок устройств и свойства /sys/block. Недоступные данные возвращаются как структурированное состояние.

### Обзор файловых систем и проверка скорости

Перечисление монтирований, ёмкости, inode, квот и деревьев lsblk выполняют платформенный адаптер; /proc/self/mountinfo помогает распознать bind-монтирования. Для сетевых точек statvfs работает в отдельном потоке с тайм-аутом 3 секунды, чтобы зависшее NFS/CIFS не блокировало экран. Локальные точки опрашиваются непосредственно. Псевдофайловые системы и точки с нулевой ёмкостью скрыты.

Действие B требует явного подтверждения и сообщает каталог записи, а не только точку монтирования. Используется доступный для записи каталог на той же файловой системе: точка монтирования, если она доступна, иначе подходящий каталог пользователя. Это не даёт принять домашний каталог под / за тестовую область корневой файловой системы.

Для теста tempfile.mkstemp создаёт файл с режимом 0600. Записывается максимум 256 MiB и не более 25% доступного пользователю места или квоты. Данные несжимаемы и различаются между блоками, чтобы сжатие или дедупликация не дали фиктивный результат. Затем вызываются fsync и, по возможности, posix_fadvise с DONTNEED, читается файл и удаляется. Тайм-бюджет делится между записью и чтением; fsync нельзя надёжно ограничить. Чтение может пройти из клиентского кэша, если NFS игнорирует сброс кэша. Перед тестом удаляются только принадлежащие пользователю пробные файлы старше часа из выбранного каталога. Одновременно выполняется один тест.

## Особенности отдельных файловых систем

<a id="chuvstvitelnost-k-registru"></a>
### Чувствительность к регистру

Пути сохраняются точно так, как их возвращает os.scandir. На файловой системе без учёта регистра один каталог может быть указан с разным регистром, но обход всегда начинается с корня и использует фактическое написание имени. Запросы к базе сравнивают строки точно, поэтому между сканированиями важно задавать корень одинаковым образом.

### Разреженные файлы

Logical использует st_size, Allocated — st_blocks × 512. Разреженный файл размером 1 GB с занятыми 4 KB показывает около 1 GB в Logical и 4 KB в Allocated/Unique. Без st_blocks последние две метрики показывают Unavailable.

### Жёсткие ссылки

Logical и Allocated учитывают каждый видимый путь. Unique группирует записи по (st_dev, st_ino) и приписывает выделенные байты лексикографически первому абсолютному пути в корне сканирования. Остальные ссылки получают ноль Unique и указывают путь-владелец. Результат не зависит от числа потоков; совпадающие inode на разных устройствах не объединяются.

### Блоки каталогов

Каталог — тоже файл: он содержит имена, и файловая система выделяет ему блоки. В ext4 любой каталог занимает 4 KiB. В xfs небольшие имена помещаются в inode, но после его заполнения каталог получает дополнительные блоки.

- **Logical** учитывает только файлы и ссылки; собственный st_size каталога не прибавляется, поскольку он не является содержимым пользователя.
- **Allocated** суммирует st_blocks × 512 файлов, ссылок и каталогов, включая сам каталог. Поэтому дерево без файлов не имеет нулевой занимаемый объём.
- **Unique** делает то же с исключением жёстких ссылок. Каталог не может быть дубликатом, поэтому его блоки учитываются один раз.

du исключает повторные inode, поэтому для дерева с жёсткими ссылками du -s --block-size=1 соответствует **Unique**. Allocated больше на байты повторных ссылок. Собственные выделенные байты каталога включают его блоки и блоки прямых файлов/ссылок, но не подкаталогов.

<a id="setevye-fs"></a>
### Сетевые файловые системы (NFS, CIFS, sshfs)

Число потоков определяется измеренной задержкой на элемент, а не только именем файловой системы. Тип монтирования указывает, является ли сканирование зависимым от задержки; измерение выбирает число потоков. Берётся худшее из выборки 64 элементов корня (около 75 мс) и среднего времени GETATTR, которое ядро накопило для NFS в /proc/self/mountstats (если было менее 100 вызовов, оно не используется). Выборка корня может быть слишком оптимистичной, если метаданные уже закэшированы.

| Задержка на элемент | Потоки |
|---|---:|
| Менее 0,5 мс (прогретые NFS, GPFS) | 8 |
| От 0,5 мс | 16 |
| От 1 мс (sshfs, CIFS через WAN) | 32 |
| От 3 мс (объектное хранилище через FUSE) | 64 |

Уровни получены по тестам с искусственной задержкой на каждый элемент: при 5 мс время снизилось с 25,1 с на одном потоке до 3,38 с на восьми и 0,88 с на 64; при 1 мс оптимум был 32. Для локального диска действует ограничение по числу CPU, для ожидающего ответа сервера — нет. Однако построение узлов потребляет CPU, поэтому бюджет CPU всё равно может снизить число потоков. В пакетном задании или CPU-ограниченном контейнере учитываются видимые CPU; на личной машине — свободная доля по минутной нагрузке; на общем узле — доля простаивающей мощности после учёта других пользователей.

Средняя стоимость сканирования — около 160 мкс CPU на элемент. На измеренном NFSv3 krb5p 16 потоков обработали 1,17 млн каталогов и 4,93 млн файлов за 368 с, использовав 986 CPU-секунд. Примерная загрузка ядра потоком равна 160 мкс, делённым на задержку элемента, в диапазоне от 0,02 до 1 ядра. При 0,65 мс один поток занимает около четверти ядра, при 5 мс — около 0,03. На 128 CPU с нагрузкой 0,5 и пятью другими пользователями доля 21 ядро даёт 84 потока, поэтому ограничивает сетевой уровень 16; при нагрузке 120 остаётся минимум 2. На машине с двумя ядрами и задержкой 5 мс доступен весь уровень в 64 потока. При доступной памяти ниже 512 MB обход последовательный.

Для automount учитывается реально смонтированная поверх autofs файловая система. Если записи имеют одну точку монтирования, выигрывает последняя, так как порядок соответствует наложению. Неразвернувшийся триггер один раз открывается для монтирования, затем таблица читается снова. Это не позволяет ошибочно исключить смонтированный NFS как псевдофайловую систему.

На сетевых файловых системах задержка каждого os.scandir выше, mtime может иметь меньшую точность или рассогласование часов клиента и сервера. База снимков по умолчанию остаётся локально в XDG_DATA_HOME, а не на сетевом ресурсе.

### Файловые системы FUSE

FUSE (sshfs, rclone, s3fs) обычно работает, потому что сканер использует стандартные POSIX-вызовы. Скорость зависит от реализации; os.scandir может не получать оптимизацию d_type и перейти к stat для каждого элемента. Все монтирования fuse.* считаются зависящими от задержки и используют те же уровни потоков, независимо от того, удалённое ли хранилище. Запрос через FUSE как минимум проходит контекстные переключения к пользовательскому daemon, а в худшем случае обращается к объектному хранилищу. virtiofs и overlay не входят в эту категорию.

### OverlayFS

Сканер видит объединённое представление. Размеры соответствуют видимым данным. Очистка удаляет только из верхнего (записываемого) слоя; файл может сохраниться в нижнем слое и появиться снова после пересоздания overlay.

### tmpfs / ramfs

Поддерживаются. Размеры в tmpfs относятся к файлам в памяти, поэтому инструменты для оценки использования диска могут вводить в заблуждение для /tmp и /dev/shm.

### FAT32 / exFAT

Символических ссылок в FAT нет. Точность времени изменения FAT32 — 2 секунды. Размеры файлов точны.

### Btrfs и ZFS

st_size показывает логический, а не дедуплицированный или сжатый размер. Снимки, подтома и reflink в Btrfs означают, что фактически освободившееся место не видно по дедупликации; инструмент показывает видимый размер, а не физическое распределение. Похожее ограничение действует для ZFS: сжатие и дедупликация могут изменить физическое использование. По умолчанию ZFS скрывает снимки через snapdir=hidden; при snapdir=visible они видны как полные копии в .zfs/snapshot/<name> и исключаются политикой каталогов снимков.

### Каталоги снимков

Системы хранения публикуют копии тома только для чтения под фиксированными именами: NetApp .snapshot в корне каждого NFS-тома (в CIFS — ~snapshot), ZFS .zfs/snapshot при snapdir=visible и VxFS .ckpt. Каждый дочерний каталог — полная копия дерева. На NetApp каждый также является автоматическим NFS-монтированием, поэтому политика «пересекать файловые системы» сама по себе от них не защищает.

Затраты растут пропорционально числу сохранённых снимков. В измеренном экспорте NetApp было семь снимков, дерево включало 1 173 122 каталога, 4 931 204 файла и 10,02 TB. При соблюдении границы сканирование заняло 368 секунд с 16 потоками. Без исключения обход повторил бы объём восемь раз и показал около 80 TB для тома размером 10 TB.

Дочерние каталоги снимков по умолчанию исключены, но остаются в отчёте как граничные узлы с причиной snapshot directory. Имя достаточно для решения, поэтому каталог не открывается: чтение .snapshot может инициировать automount. Сам корень не исключается, поэтому конкретный снимок можно проверить, указав его как корень. Для включения всех снимков используйте --include-snapshots или scan.exclude_snapshot_dirs = false.

Содержимое снимков нельзя освободить обычной очисткой, а их место уже учтено как резерв снимков. Чтобы не посчитать те же байты повторно, для учёта диска их следует пропускать.

### procfs / sysfs / devfs

Дочерние точки монтирования псевдофайловых систем по умолчанию исключены и отображаются как граничные узлы политики. Явно указанный корень (например, /proc, tmpfs или overlay) сканируется. Включить дочерние псевдофайловые системы можно флагом --include-pseudo или параметром scan.exclude_pseudo_filesystems = false. Обзор ФС и сканер используют одну классификацию.
