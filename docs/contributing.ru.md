# Участие в разработке

Руководство для разработчиков, работающих над disktide. Для общей карты модулей см. [Архитектуру](architecture.ru.md).

## Настройка

    git clone <repo-url> disktide && cd disktide
    uv sync --locked

Команда создаёт редактируемое окружение .venv по зафиксированному uv.lock, включая зависимости разработки (pytest, pytest-asyncio, pytest-xdist, textual-dev).

## Проверки

    uv run pytest tests/ -v
    uv run pytest tests/test_scanner.py -v

Тесты корутин PathSuggester используют @pytest.mark.asyncio. Большинство тестов приложения Textual запускают асинхронный сценарий через asyncio.run(...) и app.run_test(); придерживайтесь стиля соседних тестов.

### Воспроизведение ошибки только из CI

Runner GitHub использует контейнер ext4 с двумя ядрами. tests/hostshape.py моделирует различия среды:

| Форма | Что моделирует | Пример проблемы |
|---|---|---|
| readdir | Порядок файловой системы вместо порядка создания для os.scandir и результатов scheduler.scan_dir, включая C backend | Сортировка откатывается к порядку ФС при entry_chunk_size=1 |
| medium | Невозможно прочитать rotational-флаг sysfs, носитель unknown | Значок получает сырой стиль Rich вместо роли цвета |
| cores | Два CPU в os.cpu_count() и os.sched_getaffinity() | Выбор числа потоков и автоматическое ограничение live_scan_render |
| sleepless | time.sleep мгновенно завершается | Только диагностика; ломает тесты, использующие сон как инструмент |

Перед каждым запуском тестов число ядер закрепляется на DEFAULT_CPUS; форма cores специально проверяет другой результат. taskset/--cpus меняют планирование, но не значение os.cpu_count(), поэтому не воспроизводят форму cores.

## Структура проекта

Полный список находится в [архитектурном обзоре](architecture.ru.md). Основные каталоги: src/disktide/ — код; tests/ — тесты; assets/ — стили TCSS; tool/ — инструменты разработчика; docs/ — документация.

## Соглашения кода

Используйте возможности Python 3.10+: объединения X | Y, dataclass с slots/kw_only, zip(strict=True); match не используется. tomllib и StrEnum импортируйте из disktide._compat (там обратная совместимость для Python 3.10). Все публичные API должны иметь аннотации типов; каждый модуль начинается с from __future__ import annotations. Для моделей используйте dataclass с slots=True.

### Границы модулей

- scanner/, storage/, cleanup/ и viz/ не импортируют Textual и должны тестироваться без запуска приложения.
- services/ не зависит от Textual; screens/ и widgets/ могут импортировать нижележащие слои.
- CLI и TUI не вызывают напрямую примитивы безвозвратного изменения файловой системы — только через CleanupService.
- Декларативные загрузчики политик не выполняют код автора правила.

### Граница импортов при запуске

app.py не импортирует экраны режимов и сервисы на уровне модуля. Экраны импортируются внутри _launch_explorer(), сервисы — ленивыми свойствами при первом обращении. Завершение приложения читает уже созданные поля, чтобы выход с приветственного экрана не создавал сервисы только ради их немедленного закрытия. tests/test_startup_imports.py проверяет число загруженных модулей disktide.

### Сервис сканирования и потребители

Прикладной код передаёт ScanRequest в ScanService и не создаёт ScanEngine напрямую. Потребители Textual вызывают app.call_from_thread() только из callback диспетчера. Используйте ScanProgressSnapshot, NodeAggregateUpdated и итоговый ScanRun; не пересчитывайте отдельный набор итогов. Исключения потребителей изолируются; для новых потребителей добавляйте регрессионный тест. Потоки сканирования читают прямые элементы каталога; потомки планируются через TreeScanScheduler, без рекурсии в worker. ScanEngine().scan(path) сохраняется для совместимости сценариев tool/.

### Backend событий файловой системы

Backend реализуют collectors.events.base.EventBackend и передают только нормализованные подсказки, без логики представления или хранения. Необязательные пакеты проверяются и импортируются лениво. События не являются авторитетными итогами: снимки записывает только полная сверка. Переполнение, предел наблюдений, потеря корня и перезапуск должны сохранять degraded-состояние.

## Расширение сканера

src/disktide/scanner/_scanfast.c читает каталог и получает метаданные его элементов в одном освобождении GIL. Расширение необязательно: если импорт недоступен, disktide/scanner/accel.py использует _scanfast_py.py. Оба варианта должны возвращать одинаковое дерево.

<a id="rasshirenie-v-rabochey-kopii"></a>
### Расширение в рабочей копии

Editable-установка собирает расширение. pip install -e . и uv sync запускают тот же hook hatch_build.py, что и сборка wheel; для editable он компилирует объект рядом с исходником в src/disktide/scanner/. Это важно: editable-пакет указывает на <root>/src, поэтому импорт разрешается в реальном src/disktide/, который имеет приоритет над каталогом disktide/ из wheel без __init__.py. Расширение, собранное во временный build-каталог, не находилось бы импортом.

Hook не запускается повторно после изменения C-файла. Пересоберите и проверьте:

    python tool/build_scanfast.py
    disktide doctor | grep Scanner

Сборочный инструмент применяет тот же поиск компилятора и macOS-флаги, затем проверяет загрузку объекта отдельным процессом. --print-command показывает команду, --output DIR задаёт другой каталог. .so игнорируется Git; удалите конкретный объект расширения, если нужно вернуться к запасному backend, либо задайте DISKTIDE_ACCEL=0 на один запуск.

Для обоих режимов запускайте набор проверок:

    uv run pytest -q -n 4
    DISKTIDE_ACCEL=0 uv run pytest -q -n 4

tests/test_scan_accel.py параметризован для обоих backend и пропускает нативную часть, если модуль не собран. Сравнить целые деревья можно так:

    uv run python tool/dump_tree.py /some/tree --backend native -o a.tsv
    uv run python tool/dump_tree.py /some/tree --backend python -o b.tsv
    diff <(tail -n +2 a.tsv) <(tail -n +2 b.tsv)

### Особенности упаковки расширения

hatch_build.py пытается собрать расширение для wheel, но пропускает его, если компилятора нет, чтобы sdist оставался устанавливаемым. Для обычного wheel объект собирается во временном каталоге и добавляется через force_include. Иначе .so из предыдущей editable-сборки мог бы попасть в универсальный py3-none-any wheel с бинарником не той архитектуры. Для editable-сборки force_include_editable включает объект в RECORD, чтобы pip uninstall удалил его.

Компилятор ищется по порядку: переменная CC, конфигурация интерпретатора, cc, gcc, clang. Быстрая проверка запасной сборки: CC=/bin/false uv build --wheel или DISKTIDE_NO_EXTENSION=1. В macOS расширение — bundle, используется -bundle -undefined dynamic_lookup; ARCHFLAGS учитывается при перекрёстной сборке.

## Проверка дистрибутива

    uv build
    uv run python tool/verify_distribution.py

Проверка принимает cp3xx wheel с disktide/scanner/_scanfast*.so или py3-none-any wheel без скомпилированного кода. Иной нативный код означает стороннюю зависимость, которую проверка должна обнаружить.

CI устанавливает wheel в чистую среду и ограничивает поставку 20 runtime-дистрибутивами и 20 MiB, без стороннего нативного расширения. Также устанавливает sdist с компилятором и с CC=/bin/false и проверяет backend. Отдельная среда проверяет обнаружение событий в disktide[watch]. Порядок создания релиза см. в [процессе выпуска](release-process.ru.md).

## Практические инструкции

### Добавление поля конфигурации

1. Добавьте поле в подходящий dataclass: ScanConfig, MonitorConfig, CleanupConfig, UIConfig, KeysConfig или HostPaths.
2. Добавьте сериализацию в save_config(): пропускайте None для необязательных значений, строки записывайте через _toml_str.
3. Добавьте чтение в load_config() через типизированные помощники _table, _int_value, _bool_value, _str_value. Неверный тип вызывает ConfigError с названием секции и ключа и завершается в CLI кодом 2. Неизвестное этой версии значение (тема, форма, привязка) заменяется значением по умолчанию.
4. Добавьте round-trip тест в tests/test_config.py.

### Добавление миграции базы

1. Увеличьте CURRENT_VERSION.
2. Добавьте DDL под новую версию в MIGRATIONS.
3. Поместите заполнение данных в MIGRATION_CALLBACKS; оно выполняется в той же транзакции.
4. Сохраните резервное копирование и откат.
5. Добавьте тесты успеха, сохранности старых данных и прерванной миграции.

Не фиксируйте новую версию схемы до успешного DDL/заполнения. Не заменяйте неизвестную старую политику текущими значениями по умолчанию и не «чините» повреждённую базу её удалением.

### Добавление правила очистки

Дополните TOML-схему v1 в cleanup/rulepacks/ или создайте новый набор. Схема содержит имя/версию/описание и декларативные правила с шаблонами, индикаторами родителя, возрастом, риском, категорией, подсказкой восстановления и уверенностью. В правилах нет команд, hook или executor. Если универсальное действие небезопасно, используйте default_action = "detection-only". Проверяйте положительные и отрицательные случаи, индикатор, границу возраста, ошибочную схему, оценку и режим только обнаружения. Сохраняйте поддержку старых планов CleanupPlan.

### Добавление экрана

Создайте класс textual.screen.Screen в screens/, задайте BINDINGS и compose(). Каждой привязке нужен id вида myscreen.action; добавьте его в перечень disktide/keys.py, ALL_IDS и keys.SECTIONS. Иначе клавиша не появится в ? и её нельзя переназначить. Экран подключается в app.py внутри _launch_explorer(), а режим — через DiskTideApp.BINDINGS и action_switch_mode(). Стили задавайте в DEFAULT_CSS экрана. assets/default.tcss не загружается: CSS_PATH в src/ отсутствует. Стили, которым нужно перекрывать DEFAULT_CSS виджета Textual, задаются в DiskTideApp.CSS.

### Добавление визуализации

Создайте layout/rendering в viz/ и возвращайте Rich Segments; заполнение рисуйте цветом фона пробелов, не блочными символами (см. disktide.glyphs). Используйте VisualState/VisualDelta, не реализуйте классификацию роста независимо. Создайте виджет Textual, который получает готовую модель, затем добавьте TabPane и локальное сочетание клавиш. Проверяйте обычный и diff-режимы, неполные/несовместимые данные, безопасный режим без цвета, узкое окно, resize и большое ограниченное дерево.

## Советы по проверкам

- **Сканер:** фикстуры tmp_path с настоящими деревьями.
- **ScanService:** все терминальные состояния; после терминального события новых событий нет; повторное воспроизведение строит ту же view model.
- **База:** :memory: или tmp_path; фикстура db из tests/test_storage.py создаёт мигрированную базу.
- **Асинхронность:** @pytest.mark.asyncio для корутин; asyncio.run(...) и app.run_test() для сценариев Textual.
- **Не читайте хост напрямую:** передавайте параметры, закрепляйте конфигурацию или используйте threading.Event вместо сна.
- **Визуализация:** проверяйте макет отдельно от отрисовки; состояния, координаты, пробелы, идентичность выбранного пути, размер 80×24, безопасный режим и быстродействие на 100 тыс. узлов.

## Инструменты разработки

Основные скрипты в tool/: gen_activity создаёт активность файлов для monitor/watch; bench_scan и diag_scan измеряют и диагностируют сканирование; make_homelike готовит детерминированную тестовую структуру; scratchguard проверяет место записи; tui_time измеряет сканирование в настоящем TUI; soak_scan и soak_memory проверяют планировщик и рост памяти; dump_tree сравнивает деревья между backend; build_scanfast пересобирает C-модуль; capture_glyphs проверяет символы в терминале; gen_palette и palette_checks контролируют темы; verify_distribution проверяет wheel/sdist и check_dependency_budget — лимит зависимостей. Полный перечень с флагами приведён в [английском оригинале](contributing.md#dev-utilities).

Для замера сначала используйте headless bench_scan, затем подтвердите результат в реальном TUI через tui_time: рисование и общий GIL могут существенно менять время. Сравнивайте замеры на замороженной копии базовой ревизии, перемежайте запуски, делайте три повтора и сообщайте медиану; различия до 10% считайте шумом. На NFS учитывайте прогрев атрибутного кэша. Для времени потоков рассматривайте CPU отдельно от wall-clock, а для памяти используйте soak_memory: RSS может расти из-за фрагментации выделителя и его нужно сравнивать с тем же сценарием базовой версии.
