# Три системных вызова вместо одного: поиск десятикратного замедления сканирования ссылок через NFS

*Разбор проблемы при выпуске v0.1.5.*

## Симптом

Между v0.1.3 и v0.1.5 сканирование домашнего каталога в кластере замедлилось примерно с 4 до 40 минут. Та же машина, те же данные, та же файловая система NFS: 6,1 млн файлов, 100 ГБ. TUI в конце концов завершал работу, но индикатор прогресса временами замирал на десятки секунд, пока один рабочий поток разбирал глубокое поддерево.

## Поиск причины

Потоковый отчёт о прогрессе каждую секунду (`tool/diag_scan.py`) указал на медленные конечные каталоги: дерево `dataset/`, где в каждом подкаталоге находилось порядка 200 000 символических ссылок на общий кэш образов. Повторный запуск на одном таком каталоге с `--workers 1 --profile` сразу выявил причину. Для 215 339 элементов обход занял 89,5 с; вверху отчёта cProfile оказались:

    215,339  posix.stat                       81.0 s  classify_symlink (переход к цели)
    215,339  posix.DirEntry.stat               0.7 s  собственный stat ссылки
    215,339  posix.readlink                    0.3 s  текст цели ссылки

Для каждой символической ссылки обход выполнял **три круговых обращения к серверу NFS** вместо одного в v0.1.3:

1. `entry.stat(follow_symlinks=False)` — получить размер самой ссылки. Это необходимо для создания FSNode.
2. `os.readlink(path)` — прочитать текст цели. Этот вызов безусловно добавили в v0.1.4, чтобы показывать в дереве обозначение `-> /target`.
3. `os.stat(path)` — перейти по ссылке и определить, указывает ли она на каталог, файл или несуществующую цель. Этот вызов тоже появился в v0.1.4; в одном из ранних исправлений v0.1.5 его отложили для «глубоких» ссылок, но в корне сканирования он всё ещё выполнялся заранее.

На локальном SSD каждый stat занимает микросекунды, поэтому проблемы не видно. На сетевой файловой системе кластера один RPC занимает около 300 мкс; три обращения для каждой из миллионов ссылок и составили всё замедление.

## Исправление

Сделать получение всей информации о цели ссылки отложенным. Во время сканирования обход теперь выполняет один системный вызов на ссылку. readlink и stat с переходом по ссылке выполняются, только если интерфейс действительно обращается к этой ссылке; результат сохраняется в узле, поэтому повторная проверка ничего не стоит:

    def make_symlink_node(entry, depth):
        st = entry.stat(follow_symlinks=False)         # один обязательный вызов
        return FSNode(..., is_symlink=True)

    def classify_symlink(node):                        # вызывается интерфейсом по необходимости
        if node.link_classified: return
        node.link_target = os.readlink(node.path)      # readlink отложен
        node.link_is_dir = stat.S_ISDIR(os.stat(node.path).st_mode)
        node.link_classified = True

Подпись дерева упрощается корректно: ссылка, которую пользователь ещё не выбирал, отображается только именем; стрелка `-> /target` появляется, когда пользователь обращается к ней. Панель Подробностей и действие `i` уже вызывали classify_symlink с защитой от повторного обращения, поэтому интерфейс менять не пришлось.

Небольшое уточнение сохраняет ожидаемое поведение в типичном случае. Запуская `disktide ~`, пользователь рассчитывает увидеть цели нескольких ссылок в корне домашнего каталога без отдельного щелчка по каждой. Поэтому движок заранее классифицирует **первые 100 ссылок в корне сканирования** (только в корне — на более глубоких уровнях классификация полностью отложена). Сто ссылок почти не заметны: в худшем случае около 60 мс сетевых задержек NFS. Этого достаточно для обычного домашнего каталога, а ограничение не даёт снова замедлить случай, когда сам корень содержит 215 000 ссылок.

## Цена изменения

По сравнению с прежней немедленной классификацией есть три небольших и честно обозначенных компромисса:

1. **Стрелка `-> /target` в дереве.** Она видна для первых 100 ссылок в корне и для любой ссылки, которую пользователь уже выбирал (результат хранится в узле). Непросмотренные ссылки показывают только имя. Для ссылки, которую открыл пользователь, данные в Подробностях остаются достоверными.
2. **Задержка при первом выборе.** Перед показом Подробностей для ранее не выбранной ссылки выполняются readlink и os.stat. На кластерном NFS это около 600 мкс, на локальном SSD — микросекунды. Повторный выбор той же ссылки бесплатен.
3. **Подпись дерева обновляется не сразу.** Виджет дерева формирует подпись при первом добавлении строки. classify_symlink меняет узел, но не заставляет перерисовать подпись; если строку отобразили до просмотра ссылки, она останется только с именем до следующего обновления (смены метрики, сортировки или повторного раскрытия). Устареть может подпись, но не данные.

Итог сканирования, число файлов и каталогов, размер каждой ссылки, значки циклов и доступа, а также действие `i` работают как прежде.

## Результаты измерений

Изолированный конечный каталог, 215 339 ссылок, `--workers 1`, два последовательных запуска в одном сеансе:

| Сборка | Время | Скорость (файлов/с) | Вызовы `posix.stat` |
|---|---:|---:|---:|
| v0.1.5 до исправления | 89,5 с | 2 406 | 215 341 |
| v0.1.5 после исправления | 8,4 с | 25 706 | около 2 |

**В 10,7 раза быстрее на тех же данных, машине и NFS.** Основной системный вызов для каждой ссылки исчез; остался entry.stat, который получает размер самой ссылки, как и в v0.1.3. (Ограничение на 100 ссылок добавили после этих измерений. Оно выполняет не более 200 дополнительных предсказуемых вызовов в корне — около 60 мс на этой NFS, меньше погрешности теста.)

Полный домашний каталог: 6,1 млн файлов, 100 ГБ, стандартное число рабочих потоков:

| Сборка | Время | Скорость (файлов/с) |
|---|---:|---:|
| v0.1.3, исходная версия | 244 с | 25 010 |
| v0.1.5 до исправления | 2 386 с | 2 558 |
| v0.1.5 после исправления | 195 с | 31 268 |

**Восстановлено замедление в 12,2 раза; результат на 20% быстрее исходной v0.1.3.** Вместо ситуации «сканирование не заканчивается» получили «сканирование заканчивается немного быстрее версии до регрессии».

## Вывод

Добавляя функцию «богатого интерфейса», считайте системные вызовы на каждый элемент горячего пути. Два дополнительных вызова на файл незаметны на локальном SSD, но замедляют работу в десять раз на удалённом хранилище. Обычно помогает один подход: откладывать операцию до тех пор, пока пользователь не запросит данные, и кэшировать результат.

Обнаружить и устранить проблему помогли ещё две вещи:

- Одноразовый скрипт диагностики `tool/diag_scan.py` с отчётом каждую секунду, детектором зависания и необязательным профилем cProfile. Без профиля казалось, что «сегодня медленно работает NFS». С профилем хватило одной страницы вывода, чтобы назвать функцию.
- Независимый от версии инструмент `tool/bench_scan.py`, который позволяет сравнить любой прошлый релиз и получить честную базовую линию. Результат 244 с для v0.1.3 превратил «кажется медленно» в измеримый факт: «замедление в десять раз».
